# First-answer latency: production-host bottleneck scan

**Run:** 2026-09-27 PDT on `home-cortex-0`, using the production Ollama
service (`0.34.4`, `qwen3.5:9b`, Q4_K_M, 16,384 requested context, RTX 2060
SUPER 8 GiB). The [deployed-package summary](2026-09-27-speed-scan-summary.json) records
model, package, prompt, schema, fixture, and dataset fingerprints. This was a
loopback HTTP server with an invented graph and in-memory conversations; it did
not access the household database or replace the live API. The harness loaded
the installed `/app` package. One warmup iteration per case was excluded.

| Route | n | First byte P50/P95 | First answer P50/P95 | Complete P50/P95 |
| --- | ---: | ---: | ---: | ---: |
| Household fact | 9 | 42/43 ms | **1,593/1,714 ms** | 1,593/1,715 ms |
| Age threshold fact | 6 | 42/43 ms | **2,120/2,130 ms** | 2,122/2,131 ms |
| Mutation preview | 3 | 44/44 ms | 1,911/1,915 ms | 1,911/1,916 ms |
| Ordinary steward chat | 3 | 42/43 ms | 2,005/2,046 ms | 2,329/2,389 ms |
| Bare model chat | 3 | 44/44 ms | 205/208 ms | 374/380 ms |
| Discourse follow-up | 6 | 43/44 ms | 2,303/2,737 ms | 2,305/2,738 ms |
| Two simultaneous facts | 6 | 40/59 ms | 1,877/2,513 ms | 1,878/2,513 ms |

All 39 measured streams had nonempty content and no HTTP or SSE errors. The
early SSE byte is a comment/role frame, not answer text. The multi-intent cohort
(3 additional streams) produced content at 1,023/1,026 ms P50/P95, but this
timing probe does not score its decision or answer. It cannot clear the
multi-intent safety gate.

## Where a warm fact request waits

The median fact request reached its first answer at 1,593 ms. The semantic
planner consumed 1,590 ms of that, including a 1,562 ms Ollama call. Across
the fact samples, Ollama reported 11,109 input tokens, 47 output tokens,
520 ms prefill, 887 ms generation, and about 103 ms of residual model-request
work at the median. Schema output construction took about 4 ms; synthetic
identity resolution, in-memory append, graph execution, and rendering each
took less than 1 ms. These independently computed medians do not add exactly.

The age-threshold case generated more structured output (median 74 tokens)
and spent 1,405 ms generating it; its first answer arrived at 2,120 ms. The
ordinary steward chat route waited about 1,050 ms for intent interpretation,
then roughly 938 ms to the first content token from its second model call.
Three of six discourse follow-ups needed a semantic retry. During the probe,
the model used about 6.8/8 GiB of GPU memory and the GPU was busy; the API
process was comparatively idle. A separate read-only proxy `/health` check
was around 1.2/1.6 ms P50/P95, but is not a measure of the full live request
path.

The current candidate prompt for one representative fact comprised 132
messages, about 47 KB of message content and a 40 KB structured-output
schema. The varied-request
Ollama probe saw the **first planner JSON fragment** at 600–726 ms and the
complete planner result at about 1.5–2.0 s; it reported about 507–572 ms
prefill. Repeating an identical prompt gave 163–234 ms to its first fragment
because prefill collapsed to about 68 ms with exact-repeat cache reuse. That
cached result is not a household-traffic estimate. A planner fragment is
not a validated fact answer: the executor must wait for the complete plan.

## Implications and next experiment

The current warm route cannot meet the ticket's 300 ms P50 / 800 ms P95
first-answer stretch target through Python, HTTP, or warmup tuning alone.
Even its median structured-output generation (887 ms) exceeds the P95 target
before the 520 ms prefill. Automatic warmup helps cold or evicted-model
requests; this run found the model already resident, so warmup sent zero
inference requests and only checked residency (about 14 ms).

The next useful experiment is a paired, isolated model/runtime/hardware
candidate with the same streamed HTTP probe and the standard semantic,
mutation, bilingual, and multi-intent gates. The installed `qwen3.5:4b`
model has a historical faster planner result, but its 2026-09-24 full run
failed four partial multi-intent cases; it is not a safe drop-in. A previous
prompt-compression experiment caused held-out regressions without a reliable
latency win. A faster decoder or substantially stronger inference hardware
is the most plausible route to near-instant **answer** text while retaining
the complete-plan contract. Prompt/schema reduction can be tested only with
paired correctness evidence.

Cold-boot time, an arriving user during warmup, browser paint, new-conversation
creation, live DB persistence, and the deployed ingress path remain separate
unmeasured parts of the ticket. No live service was restarted or promoted.

`scripts` from `/tmp/hc-candidate-20260927` in the API container. The
[candidate summary](2026-09-27-candidate-summary.json) has its own package and
prompt fingerprints; model, runtime, fixture, and dataset were the same. Both
were warm sequential runs, not a randomized paired experiment.

The candidate's fact model call still took about 1,495 ms at the median:
491 ms prefill and 895 ms generation for 47 output tokens. The discourse
cohort had no semantic retries in six candidate turns, versus three in six
deployed-package turns. This probe does not establish why that changed or
score the answers. A separate current-source `hc-bench standard` run on the
same GPU host scored 108/119 planner cases, 21/21 mutation classifications,
and 7/7 multi-intent handling, with both absolute safety gates passing. The

## Focused output-transport trials (later on 2026-09-27)

The production-host GPU was used for two disposable, synthetic structured-plan
experiments. The running API and Ollama configuration were unchanged. Both
experiments retained complete JSON validation followed by the canonical
semantic-plan validator before any execution. The cases covered identity,
household count, numeric age, ordinary chat, multi-intent refusal, mutation
preview, and kinship; their checks covered branch selection, the age operator,
and preview mode, not full answer correctness. Seven of seven focused checks
passed for each candidate. These were small, alternating-order diagnostics,
not promotion-grade latency or accuracy benchmarks.

| Output shape | Example identity output tokens | Age output tokens | Observed result |
| --- | ---: | ---: | --- |
| Canonical envelope | 47 | 74 | Existing serving shape |
| Short branch envelope | 37 | 63 | Age and multi-intent wall times increased in the focused run, despite fewer generated tokens |
| Short nested key aliases | 43 | 70 | Saved only a few tokens; no useful decode reduction |

The branch-envelope trial showed about 180–210 ms less reported generation
work on individual fact cases, but its additional model-request work varied
and erased that saving for age and kinship. Its seven-case median wall time
was 1,752 ms versus 1,925 ms for canonical output; the age case rose from
1,975 to 2,286 ms and multi-intent from 1,000 to 1,206 ms. These small
samples do not support a route-wide P95 win. In the alias trial, alternating
prompt formats repeatedly caused roughly 9 s full prefill on a format switch;
those alternating wall times cannot estimate steady-state serving latency.
The production package's synthetic planner prefix was restored after testing.

Neither candidate was added to serving code. They do not close the measured
roughly 500 ms varied-prompt prefill and 900 ms plan-generation budget, and
the focused checks do not replace the standard semantic and mutation gates.

An isolated current-source `qwen3.5:4b` standard-suite attempt was also
stopped after 10 of 119 planner cases. Following the first request, several
calls took about 14–15 s and `ollama ps` showed no resident model between
them. This run was not a warm latency or semantic score, and the cause of
the residency churn was not established. The benchmark process was terminated;
a synthetic production-package 9B planner call then completed, and `ollama ps`
again showed `qwen3.5:9b` resident at 16,384 context on 100% GPU. No model
switch was promoted. A subsequent varied synthetic production-package plan
completed in 1,766 ms with a 2.5 ms reported model load, consistent with a
warm runner rather than the 14–15 s churn seen during the 4B attempt.

## Planner-shaped cold-prefix warmup trial (later on 2026-09-27)

The [bounded synthetic summary](2026-09-27-planner-prime-summary.json) used
the **unified** planner prompt and output schema that the mutation-enabled
steward actually serves. The model remained resident at 16K context throughout;
these are direct Ollama calls from the isolated candidate package, not HTTP
first-answer measurements or a cold model boot. The 11.1K input-token prompt
was not already primed after an intervening read-only-planner probe.

| Unified request | Prefill | Generation | Wall |
| --- | ---: | ---: | ---: |
| Synthetic planner prime, one output token | 8,901 ms | ~0 ms | 9,306 ms |
| Different question after prime | 512 ms | 1,045 ms | 1,657 ms |
| Another different question | 513 ms | 873 ms | 1,501 ms |
| Exact repeat after varied questions | 69 ms | 1,047 ms | 1,265 ms |

The one-token prime reached `done_reason=length` by design; it did not produce
an executable plan. Its purpose was to fill the model's shared prompt state in
the background. The next different question reused enough work to avoid the
8.9 s full prefill, although the runtime did not report restored token or
checkpoint counts. The 55.6 KB common serialized message prefix is not an
actual KV-hit count. The varied-request ~510 ms prefill remains a model-call
bottleneck. This small sequential probe does not establish cold-boot P50/P95,
the impact of an arriving user during warmup, or answer correctness.

The local automatic Ollama warmup now accepts the serving planner's synthetic
messages and structured schema from the API composition root. On a missing
resident model, its single bounded background call requests just one output
token, then verifies residency. The default bare-provider fallback remains a
one-token `OK` call. The source is not deployed; the live service and model
settings were unchanged. If Ollama is already resident when the API starts,
the existing residency guard skips this prime. That case needs a separate
safe cache-state/deduplication design before claiming all API restarts are
covered. The full local deterministic suite passes: **1,005 tests**.
On the host, loading edge schemas, loading the runtime catalog, and building
the synthetic unified warmup request took 2.5, 44, and 26 ms respectively in
one process measurement; these are startup preparation costs, not cold-model
readiness times.
